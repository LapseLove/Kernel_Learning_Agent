01 / System

让优化经验能查、能追溯

KernelWiki 是面向 Blackwell 和 Hopper 的 GPU kernel 优化知识库，仓库根目录的 SKILL.md 也是 Claude Code 的使用入口。工程师和 Agent 可以先找技术线索，再沿页面 ID 回查 PR、论文、作者文章或实现。

  1. Source

    sources/ 收录材料

    每篇 PR、文档或文章有独立记录。原样保存的 patch 或代码另放在 artifacts/。

  2. Synthesis

    wiki/ 解释机制

    把多条材料组织成技术或 kernel 页面，用 YAML 元数据记录架构、来源和证据状态。

  3. Navigation

    queries/ 派生索引

    生成器读取资料页与综合页的元数据，产出架构、问题、技术等导航。索引也可以直接读。

论文和 PR 往往从不同角度描述同一个机制。综合页把它们连起来，并保留各自出处。命令行的 query.py 直接扫描 wiki/ 和 sources/；queries/ 提供按主题浏览的入口。

02 / Ownership

谁读、谁判断、谁写文件？

用同一个 FA4 问题看一次交接。这里区分回答用户时的产出，以及维护仓库时写入的文件。

供 Agent 使用
SKILL.md 告诉 Agent 何时用库、该选哪个工具、回答要带哪些证据。综合页、来源、索引和归档是它读取的材料，人也可以直接查看。
查询脚本产出
query.py 打印按规则排好的候选；get_page.py 按 ID 或路径取页，再按选项显示所引资料的片段。一次查询只读取本地库。
Agent 的产出
把问题转成查询参数，挑值得读的候选，核对架构、证据级别和来源，最后写出带引用的解释、适用边界和下一步验证。例如在 FA4 的回答里把 SM100 归类、上游实现和待确认的当前框架派发分开写。
维护阶段写入
脚本生成候选记录、部分 PR 来源页和导航索引。wiki/ 的机制综合与证据取舍属于编辑工作，维护者可以让 Agent 起草或修订并审查。现有页面的具体作者归属要查其提交记录。

    05 / Maintenance
    新 PR 怎样进入知识库？
    

    下面以 PR 来源为例。FA4 查询所追的论文与作者博客也属于 sources/，各有自己的来源记录。
    

      
  
    1. 刷新候选账本
      refresh_candidate_ledger.py 从 GitHub 搜索候选并补取 PR 及文件证据。已有编号跳过；新编号由范围规则给 include 或 exclude，取不到证据时记 defer，再写入 candidates/。刷新规则 ↗ · 账本约定 ↗
      2. 
  
    2. 从纳入项生成来源页
      generate-pr-pages.py 读取尚未生成的 include 条目，经 gh api 取 PR 和文件列表，再核查范围。通过后按模板写入 sources/prs/。独立的 artifacts/ 可保存原样 patch 或文件，并用 PROVENANCE.yaml 记录出处。生成逻辑 ↗ · 归档样例 ↗
      3. 
  
    3. 编辑综合页
      维护者按问题挑选来源，解释机制、适用边界和证据强度，再把来源 ID 写进 wiki/。Agent 可以协助起草和核对。PR 生成器的输出到来源层为止。
      4. 
  
    4. 从元数据重建导航、跑验证
      generate-indices.py 读取两层 Markdown 的 YAML frontmatter，按架构、问题、技术等分组，写出 queries/ 下七份索引。验证器另外检查来源 ID 和 verified 的证据字段。读取索引输入 ↗ · 索引输出 ↗ · 验证规则 ↗
      5. 

    

    把这套结构迁移到自己的团队，先做哪一块？

    06 / Comparison
    两套系统怎样分工？
    

    KernelWiki 让读者从机制或硬件条件找知识页。BBuf 的 Model PR history 让读者从框架和模型族找变更历史。差异可以从查询返回的第一种对象看出来。
    

    
  
    KernelWiki · 找页面和来源
    
  
    查询。 扫描带 frontmatter 的单页，经架构、类型过滤与词项评分后返回页面 ID、路径和标题。Agent 再跟 sources 核实结论。
    
  
    构建。 GitHub PR 候选 → 规则账本 → 纳入项的来源页。综合页由编辑工作组织；独立脚本读取两层元数据，生成按主题浏览的索引。
    
  
    查询入口 ↗ · PR 来源页生成 ↗ · 索引生成 ↗
    
  
    Model PR history · 找档案和命中行
    
  
    查询。 先按框架、模型和语言挑本地档案，再按词频和模型名等信号给文档计分；从每份档案按原顺序打印最多六条匹配行，任一词命中即可。Agent 打开整份档案、PR diff 和当前 caller，写出带风险和验证条件的判断。
    
  
    构建。 git ls-files 选模型文件 → git log --name-only 从提交标题提取 PR 号 → 标题与路径提示过滤 → 合并旧档案中的 PR 号。生成器复用符合条件的旧卡片，经 gh api 补取需要的 PR 元数据与变更文件，再输出中英文档案。--dry-run 给候选和复用统计，在抓取与写入前结束。
    
  
    给 Agent 的指令 ↗ · 档案查询 ↗ · Git 追溯 ↗ · 重建主流程 ↗
    

    

    试读一个反例。 在 Model PR history 搜 SGLang / qwen3-core / 中文的 fused qk norm，首条是 #7723 的 FusedMoE 相关记录，因为 fusedmoe 包含 fused。这个命中行和 KernelWiki 里的 DeepGEMM 都是脚本给出的线索，是否回答原问题由 Agent 核对原文后判断。实跑命中的档案位置 ↗
