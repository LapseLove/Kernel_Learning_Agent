# mHC → DeepGEMM Mega-mHC: optimization history

Research snapshot: 2026-10-31. `case_id: mhc-mega-sm100`. This is a source audit, not a local GPU reproduction. All GitHub code links below use full PR-head SHAs, which are historical snapshots, not claims about current `main`.

## Intake before history

The operator is a **cross-sublayer residual boundary**, not attention or KV-cache computation. The DeepGEMM interface accepts `x[T,H]` BF16, `residual[T,4,H]` BF16, carried pre-mix and post/combination coefficients FP32, an FP32 projection `fn[24,4H]`, and RMSNorm weights; it produces the next residual and coefficients plus BF16 or optional FP8 normalized output. The shifted pre-mix is from the **preceding** sublayer. See the [API contract](https://github.com/deepseek-ai/DeepGEMM/blob/39d8c4cacc2c07c1fa9921c6c29c6a8a2da75359/csrc/apis/mega_mhc.hpp#L41-L87) and [shape/dtype checks](https://github.com/deepseek-ai/DeepGEMM/blob/39d8c4cacc2c07c1fa9921c6c29c6a8a2da75359/csrc/apis/mega_mhc.hpp#L116-L180). Thus KV format, head count and key count are outside this operator; they still matter to a full-model serving comparison.

For the **V4.1 shifted boundary**, the workload is conceptually: post-map and add the sublayer output to four residual streams → collapse with **carried previous** pre weights → RMSNorm the next sublayer input → project the updated streams to the next pre/post/residual-mix coefficients, including Sinkhorn projection for the residual mix. DeepGEMM's *normal* API mode omits `shifted_prev_mix` and uses the current residual-derived pre; its *shifted* mode supplies the carried pre and produces `new_prev_mix`. [API mode contract](https://github.com/deepseek-ai/DeepGEMM/blob/39d8c4cacc2c07c1fa9921c6c29c6a8a2da75359/csrc/apis/mega_mhc.hpp#L77-L87). The vLLM caller explicitly documents the shifted ordering, first-layer broadcast, and Engram injection exception [here](https://github.com/vllm-project/vllm/blob/91368b7e2330d9b36e86c6ca54c7a938efcca29b/vllm/models/deepseek_v41/nvidia/model.py#L336-L425). The performance-hole hypothesis is repeated launch and HBM traffic across these stages, plus a short-token projection with insufficient work per standalone kernel. It is a **hypothesis**, not a measured bottleneck for this workspace.

## Algorithm lineage: why mHC exists

HC widened a residual path to `n` streams and used learned pre, post and residual-mix matrices. Its unconstrained residual matrix can amplify or attenuate signals when composed over deep stacks. DeepSeek's mHC projects that matrix with Sinkhorn iterations toward a doubly stochastic matrix; row/column sums preserve the stream mean and make residual propagation stable. This is the model-level reason the Sinkhorn step exists. The [mHC paper, §§1 and 4](https://arxiv.org/html/2512.24880v2) is the source; the [DeepSeek V4 model card](https://fe-static.deepseek.com/chat/transparency/deepseek-V4-model-card-EN.pdf) confirms mHC as a V4-series model feature. The original paper's TileLang kernel fusion, recomputation and DualPipe communication overlap concern **training infrastructure**, not proof of an inference Mega-mHC speedup or of CUDA multistream serving overlap. The paper reports 6.7% extra large-scale training time at `n=4`, under its own training setup; it is not a Mega-mHC latency measurement. [Paper §4.3](https://arxiv.org/html/2512.24880v2).

Before running, ask the learner to predict:

1. **Small T:** Mega saves launch/intermediate traffic enough to beat TileLang. Falsify with same GB200 binary/weights, paired CUDA-graph replay at `T=1,8,64,256`, recording full-stage CUPTI spans and kernel list; include cold/warm cache variants.
2. **Split-K trade-off:** increasing split count improves occupancy at low `T` but increases scratch/barrier/reduction cost. Falsify by holding `T,H,SM count` constant, toggling deterministic 16-split vs heuristic or controlled split variants, and profiling CTA occupancy, scratch traffic and latency. Archive losing variants.
3. **Overlap:** side-stream coefficient generation actually hides under attention/FFN only at a bounded `T` and graph mode. Falsify with Nsight Systems traces showing concurrent kernels and producer/consumer joins, plus paired full-forward timings at `T=8,16,24,48` under matching capture. Record regression cases.

Reproduction needs GPU/driver/CUDA, exact dependency versions and source SHAs, warmup/capture policy, input distribution, baseline, trial counts, correctness tolerance, and profiler traces. None were run in this audit. A reader should now be able to state the carried-pre ordering, the launch/traffic hypothesis, the split-K choice, the vLLM/SGLang gates and fallbacks, and why the reported numbers are not interchangeable.

## Operator-level teaching correction (2026-10-31)

Read the [mHC paper's architecture and Sinkhorn definition](https://arxiv.org/html/2512.24880v2) before the kernel timeline. The model carries `R[T,4,H]` around each Attention and FFN/MoE sublayer. A boundary predicts 4 Pre, 4 Post and 16 Comb values from the residual; Pre collapses the routes to the next sublayer's `H`-wide input, while Post/Comb update the four-route state after that sublayer returns. In V4.1 shifted ordering, *carried* Pre collapses the current state and newly predicted Pre is consumed by the next boundary; see [SGLang's pinned state contract](https://github.com/sgl-project/sglang/blob/0ac7ee38c478632aee85c6537106abc37c52bdd5/python/sglang/srt/models/deepseek_v4_mhc.py#L1-L18). The canonical DAG, shape/dtype and a hand-checkable residual update are now in `cases/mhc-mega/case.json`; the HTML starts from them.

The earlier implementations did not simply fuse “mHC.” [SGLang's split-K Pre](https://github.com/sgl-project/sglang/blob/75716163c3589823d768229f5f27d067c3e0e928/python/sglang/srt/layers/mhc.py#L625-L795) reads a materialized BF16 residual and writes FP32 projection/squared-sum partials; `big_fuse` reduces them, computes the 4×4 Sinkhorn and collapses routes. [vLLM's small-T FMA producer](https://github.com/vllm-project/vllm/blob/84168f3c4379aaa6e93528475a0d7abcefbe35af/vllm/model_executor/layers/mhc.py#L418-L533) combines Post and those partials for `T≤16`, but still needs a subsequent [big_fuse epilogue](https://github.com/vllm-project/vllm/blob/84168f3c4379aaa6e93528475a0d7abcefbe35af/vllm/model_executor/layers/mhc.py#L696-L713). [SGLang's corresponding producer](https://github.com/sgl-project/sglang/blob/48c47c571038d7d651431d7b649a14e2ecb83e23/python/sglang/srt/layers/mhc.py#L908-L1145) uses `T≤32` and explicitly rounds the updated residual to BF16 before its projection; the vLLM source stores BF16 residual but projects from its FP32 local value. This numerical boundary is a concrete comparability caveat. The [Mega source](https://github.com/deepseek-ai/DeepGEMM/blob/5081f8513af57e61696de4f4f04b0e707ffb503e/deep_gemm/include/deep_gemm/impls/sm100_mega_mhc.cuh#L69-L112) instead schedules six source-defined warpgroups within a persistent SM100 launch; measured occupancy and physical traffic remain unknown.

Dispatch also follows the caller, not a kernel name. [vLLM V4.1's wrapper](https://github.com/vllm-project/vllm/blob/91368b7e2330d9b36e86c6ca54c7a938efcca29b/vllm/models/deepseek_v41/nvidia/ops/mega_mhc.py#L112-L156) has no explicit prefill/decode check. [SGLang's function named `can_use_mega_mhc_prefill`](https://github.com/sgl-project/sglang/blob/0ac7ee38c478632aee85c6537106abc37c52bdd5/python/sglang/srt/models/deepseek_v4_mhc.py#L572-L579) likewise checks device, opt-in, CP and seam, while [its stats side-stream gate](https://github.com/sgl-project/sglang/blob/0ac7ee38c478632aee85c6537106abc37c52bdd5/python/sglang/srt/models/deepseek_v4_mhc.py#L222-L247) does distinguish decode and target verify. Collective branches can take precedence over Mega, and CP prefill/row selection can close the fusion seam. The HTML's Dispatch table gives fixed-source examples; they are branch deductions, not observed runtime traces.
