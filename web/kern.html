一轮请求，
怎样跑完？

有 5 个请求在等模型。有人要继续生成，有人还有一段提示词没处理完。vLLM 决定这一轮处理哪些 token（文本小片段），kern 负责执行模型计算。 两者通过插件 kern_vllm 交接。

01 / 从请求到调用

5 个请求，为什么调用 3 次？

先数每个请求本轮要算几个 token。decode_batch 每个请求只接 1 个，prefill 可以接多个。插件按现有顺序，把相邻的同类请求尽量合成一组，再请 kern 逐组计算。

源码里怎么判断？

源码从相邻的 token 起始偏移求出各请求的本轮长度，常记为 q。最长请求只有 1 个 token 时走纯 decode 路径，按容量切组。遇到多 token 请求才走混合路径，按相邻关系和每组容量切分。

只含 1 个 token 的新提示词同样走 decode。混合路径遇到缺少 prefill 的清单会抛错，长提示词需要由 KV connector 先提供缓存。示例只展示实际请求，纯 decode 的 CUDA Graph 填充行另行处理。

02 / 放大原例中的 C、D

7 个 token 交进去，什么回来？

C 有 4 个 token，D 有 3 个。插件把这 7 个 token 交给 kern 的一次 prefill 调用。两段输入排在一起，各自仍属于原来的请求。

历史缓存留在原处

KV 缓存和递归状态是模型留给后续轮次的数据。vLLM 分配这些内存页，kern 直接用绑定好的地址读写。 上图两次复制的是本轮的输入和结果。

从插件注册到借用缓存地址

先告诉 vLLM 需要什么形状的缓存，等它分配好，再把真实 GPU 地址交给 kern。以 Qwen3.8 的一层注意力缓存 kv.l3 为例。

为什么要重绑？ vLLM 可能先用小缓存探测 CUDA Graph 占用，再换成正式缓存。插件发现用于检查的缓存张量对象换了，就在捕获前重新绑定。kern 重编译启动清单，并丢弃自身旧的 Graph 实例，避免沿用旧地址。

看一次交接。两条 GPU 队列怎么互相等？

GPU stream 可以理解为一条按顺序排任务的队列。同一条队列内天然有先后关系，跨队列要显式接上。 下面按四步追踪 C、D 的输入和输出，箭头从记录事件的一方指向等待的一方。

cuStreamWaitEvent 把等待排到 GPU 队列里，CPU 可以继续提交后面的操作。图展示依赖，实际耗时由测量确定。

示例的混合轮次直接提交 GPU 操作（eager）。在上游 FULL_DECODE_ONLY 配置中，符合条件的纯 decode 可以捕获成 CUDA Graph。事件把 kern 队列接进同一次捕获，再接回 vLLM 队列。绑定和初始化需要在捕获前完成。

03 / 从清单到 GPU

kern 怎么知道 prefill 要做什么？

模型包里的 manifest 是一份可执行清单。它写明每一步调用哪些 GPU 操作、从哪里读数据、结果写到哪里。kern 读取这份清单，把代码和权重接起来。

拆开一个真实的操作，看清单怎么写

上游 README 的 decode 示例从词嵌入开始。先给出 token 编号，再去权重表里查对应的向量，写到 hidden。顺着这次查表，可以读懂四层名字。

  1. program整份步骤清单。decode 里有多次操作调用。
  2. call清单里的一次具体调用。把 token_ids、权重表 embed 和输出缓冲 hidden 交给词嵌入操作。
  3. op操作的接口与实现。这里的 embedding 定义它接收什么参数以及怎样执行。
  4. launch一次设备代码的启动描述。此处指定了 kern_embedding_i64_bf16。

一次 program 调用可以展开成多次 GPU 启动。分组实验计的是 program 调用。

kern 单独运行时，和挂到 vLLM 里有什么区别？
独立运行 kern run
对自有状态的清单，加载时分配状态和编译。CLI 自己准备输入，驱动生成循环。
挂到 vLLM kern_vllm
先分配 kern 自己的缓冲。等 vLLM 提供缓存地址后，再绑定和编译。vLLM 驱动调度与采样。
04 / 设计动机

为什么单独做一个 kern？

假设只想优化一种模型在一类 GPU 上的 decode。通用推理引擎要兼顾许多模型、精度和 GPU，专用改动也要放进这套共享实现里。kern 把 kernel 选择和计算组合放进这个模型自己的执行包，由通用的 kern 运行时读取和执行。

改动范围清楚
在 manifest 中定位某个操作，替换它引用的设备代码，或改变融合和并行切分。上游 README 用 silu_mul 演示替换 kernel 引用。
可以独立验证和测量
kern test 用参考实现核对候选结果，kern bench 在指定形状上测时间。清单的布局和参数校验能提前发现一部分接线错误。

为什么还要接入 vLLM？

前面的五个请求由服务层排成一轮。真实服务还要管理缓存、采样和提供 API。插件让 vLLM 继续负责这些工作，同时把测试过的模型计算交给 kern。这样团队可以用线上出现的请求形状，决定下一轮该优化哪里。

接入仍需要为模型准备符合插件约定的 manifest 和缓存布局。适配工作量与收益都要按模型和负载评估。

05 / 上游实测

接入 vLLM 后，性能怎么样？

在 Qwen3.8-27B 的上游测试里，早期版本高并发吞吐落后。优化版在 AgentX 回放中吞吐更高，但尾延迟也更高。三组实验各自有对照，结果均为上游报告。

首 token 延迟看多久收到第一个 token，token 间隔看生成过程中相邻 token 等多久。p50 是中位数，p99 是约 99% 样本不超过的值。

缓存布局、测量方法和启动命令

Qwen3.8 的缓存页为什么按 832 个 token 管理？

Qwen3.8-27B 的适配版本让两类模型层使用相同大小的管理页。attention 层按小块存放 KV，GDN 层则需要放下一份递归状态。用后者的大小决定前者需要凑几个完整小块。

核对字节数和步幅

attention 每个 token 占 4 个 KV heads × 2（K、V）× 256 × 2 B = 4,096 B。64 个 token 占 262,144 B。

GDN 状态占 3 × 10,240 × 2 B + 48 × 128 × 128 × 4 B = 3,207,168 B，页容量比状态多 200,704 B。两类层各用自己的页。

KV 视图 [B,4,64,512] 的步幅以 bf16 元素计，为 [131072,512,2048,1]。GDN 视图 [B,3207168] 的步幅以 u8 元素计，为 [3407872,1]。这些数字描述存储容量与布局。

调用合并之后，怎么验证服务更快？

先确认测试跑的是同一组调用。固定版本里的离线转换会把所有单 token 请求并到一起，并把多 token 请求逐条输出。原例里两边恰好都是 3 次，喂给 GPU 的组却不同。

在线实际分组
A+B → C+D → E
离线脚本转换
A+B+E → C → D

比较逐条 prefill 和合组 prefill 时，用同一 GPU、输入、模型版本和 Graph 配置。先对比输出，再重复测量 GPU 时间和服务时延。KERN_TRACE 的时间戳来自元数据构建，GPU 计时需要单独采集。
